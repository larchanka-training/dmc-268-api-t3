# Ошибочные сигнатуры: как проверять предположение

Сигнатура — подозрительный шаблон, а не диагноз. Применять только к изменённому достижимому пути.

| Сигнатура | Как доказать дефект | Когда это не finding |
| --- | --- | --- |
| SELECT → INSERT запуска | Два worker проходят проверку; нет unique constraint/атомарного upsert | Ограничение БД есть, конфликт обработан |
| Дедупликация только по SHA | Второй explicit rerun возвращает старый run_id вопреки контракту | Это только кэш файлов, не запусков |
| Ack до durable save | Падение в этом окне теряет единственную копию работы | Работа уже принята долговечным inbox |
| Sync SDK внутри async | Реальный блокирующий I/O идёт в event loop | Вызов async либо вынесен в threadpool |
| JWT decoded, но не verified | Неподписанный/подменённый токен даёт доступ | Верификация уже в middleware |
| Получение run только по id | Пользователь другого tenant получает отчёт | Репозиторий применяет tenant scope до возврата |
| Retry publishComment | Повтор запроса создаёт второй видимый комментарий | Provider id/key сохранён и используется при повторе |
| `as DTO` для JSON | Неверный JSON доходит до логики и ломает контракт | Runtime validation уже выполнена на границе |
| Старый fetch пишет в store | Медленный ответ A заменяет уже выбранный B | Есть generation guard/отмена с проверкой актуальности |
| Ошибка модели → findings=[] | UI показывает успешное ревью после timeout | Отдельный error status запрещает такой вывод |

Пример доказательства: «При двух конкурентных событиях E обе транзакции видят отсутствие записи и создают разные run_id, поскольку уникальности event key нет». Сначала покажите отсутствие ограничения в доступной миграции. Если миграции не предоставлены — это hypothesis с просьбой о контексте.

Не называйте любую строку SQL SQL injection: параметризованный запрос является контрпримером. Не выводите недоступность сервиса только по названию timeout без трассировки ветви ошибки.
