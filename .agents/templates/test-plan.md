# План проверки поведения

- Issue и контракт: …
- Given (данные/права/состояние): …
- When (одно действие): …
- Then (наблюдаемый ответ и сохранённые эффекты): …
- Какая ошибка будет обнаружена этим тестом: …
- Уровень: unit / API / DB / broker integration.
- Команда и среда: из manifest рабочей ветки; результат заполняется после запуска.

| Сценарий | Что наблюдать | Почему нужна эта проверка |
| --- | --- | --- |
| Два одновременных повтора события | Одна запись, одинаковый run_id | Последовательный mock не выявит race condition |
| Два явных rerun на том же SHA | Два новых run_id | SHA не является ключом пользовательского действия |
| Retry одного rerun | Тот же run_id | Сетевой retry не должен повторять бизнес-эффект |
| Один ключ, несовместимый payload | Явный конфликт | Нельзя тихо вернуть отчёт от другой операции |
| Чужой tenant/run | Отказ, без утечки отчёта | JWT не заменяет проверку ресурса |
| Падение между commit и publish/ack | Работа восстанавливается без дубля | DB и broker не имеют общей транзакции |
| Ollama timeout/невалидный JSON | Ошибка или partial, не success | Пустой findings не скрывает отказ |
| 429 от VCS | Ограниченный retry с бюджетом | Не создавать бесконечный поток запросов |

Unit-тест подменяет внешний порт, а не проверяемую логику. DB-тест использует реальную уникальность PostgreSQL и отдельные сессии; SQLite не доказывает поведение PostgreSQL. Broker-тест проверяет повторную доставку после падения. До появления адаптеров эти строки — acceptance scenarios, а не готовые интеграционные тесты.
